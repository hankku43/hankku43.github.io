資料清洗流程 (Preprocessing Pipeline)

針對 POP909 資料集，以 downbeat 對齊取代等長切割，建立統一的清洗邏輯：

Downbeat 對齊

讀取 beat_midi.txt 提取強拍位置，動態建立小節視窗，適應曲速變化。並偵測保留樂句開頭的弱起拍 (Anacrusis)。

調性正規化

依 POP909 附帶的 key_audio.txt 逐段分析調性，將所有樂曲轉調至 C 大調或 A 小調，縮小模型的學習空間。

延音踏板補償

依踏板訊號延長音符 duration，並加入防重疊偵測（若延長後超過同音高的下一音符起點，則截斷）。

4 / 18

兩套切分策略 (Data Slicing)

底層清洗邏輯相同，依模型任務衍生出兩套切分方式：

4-Bar 視窗（多小節伴奏）

提供上下文給 Stage 2 伴奏生成模型，理解長期樂句走向：

  • Input：4 小節單軌（主旋律）
  • Output：對應 4 小節伴奏

→ 用於 Melody Editor 與 Advanced Mode

1-Bar 視窗（Next-Bar Prediction）

為即時伴奏打造，一次處理 2 個連續小節：

  • Input：第 1 小節雙軌（旋律 + 伴奏）
  • Output：第 2 小節伴奏

→ 用於 Realtime Piano 瀏覽器端推論

Tokenization (Symusic + MidiTok REMI)

為何選擇 Symusic？

底層 C++ 實作，在處理 POP909 全量資料集時，批次讀取與轉換速度遠優於純 Python 的 music21。

REMI 序列結構

將多軌 MIDI 編碼為一維 Token 序列。透過 Program Token 區分旋律與伴奏軌：

# Token 序列範例（雙軌合一）

[Program_0] # 宣告：旋律軌
[Bar_0] [Position_16] # 時間定位
[Pitch_60] [Velocity_80] [Duration_1.5.0]

[Program_1] # 宣告：伴奏軌
[Bar_0] [Position_16]
[Pitch_48] [Pitch_52] [Pitch_55] # 和弦

8 / 18

三種和弦預測架構（Stage 1 Predictors）

Two-Stage 流程中，Stage 1 負責從旋律預測和弦序列，我們實作了三種架構：

V1：標準 AR

Autoregressive

標準自迴歸解碼，逐 Token 預測和弦。輸出格式最單純。

V2：小節感知 AR

Bar-Aware AR

在 Target 序列中插入 Pos_X 位置標記，強化模型對拍內位置的感知，和弦切換點更整齊。

V3：非自迴歸 NAR

Non-Autoregressive

移除 Decoder Causal Mask，一次讀取完整 4 小節旋律並平行輸出所有和弦，推論速度最快。

NAR 閃爍問題與 Lookahead 平滑

問題：NAR 的和弦閃爍 (Flickering)

NAR 模型因缺乏 Token 間的強依賴，容易受局部旋律外音干擾，在相鄰位置預測出短暫跳變的和弦（如 C → G → C）。

解法：Lookahead 前向預看

推論時介入機率分佈：比較當前與下一步的 Top-1 預測，若兩者一致且下一步信心度更高，則鎖定此和弦並向後延伸，抑制短暫跳變。

另加入重複懲罰（同一和弦連續 4+ 次則降低 logit），防止過度鎖定。

平滑修正示例

Raw: [ C, C, G, C, C ]
Window: size = 2
Smoothed: [ C, C, C, C, C ]

音訊渲染引擎（Tone.js + AudioService）

為何使用 Tone.js？

原生 <audio> 標籤不支援 MIDI 多音發聲與精確 BPM 對齊。Tone.js 提供：

  • Sampler：載入真實鋼琴取樣音色
  • Polyphony：同時觸發多個音節（和弦）
  • Transport：精確 BPM 排程，確保音符觸發時間對齊

Singleton AudioService

解決 Vue 組件切換導致的 Web Audio 資源重複建立與記憶體洩漏：

class AudioService {
  constructor() {
    if (!AudioService.instance) {
      this.piano = new Tone.Sampler({...});
      AudioService.instance = this;
    }
    return AudioService.instance;
  }
}

工程挑戰與解法

挑戰 影響 解法
1. 即時伴奏有網路延遲 API 往返造成音符停頓，無法實現即時彈奏感 導入 Transformers.js，將 ONNX 量化模型移至瀏覽器端執行
2. NAR 和弦閃爍 相鄰拍預測出短暫跳變和弦，造成伴奏聽感不連貫 實作 Lookahead 平滑：比較前後步機率，鎖定穩定和弦並壓低跳變
3. 多音軌 Web Audio 破音 組件切換導致多個 AudioContext 並存，資源耗盡或發生爆音 Singleton AudioService 統一管理 Tone.Sampler 生命週期；前處理踏板補償防重疊
4. 部署安全與穩定 推論耗資源，後端需防護惡意請求 SlowAPI Rate Limit（5 req/min），MIDI 上傳限 10MB，CORS 白名單；Docker Compose 一鍵啟動
